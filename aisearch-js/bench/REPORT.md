# aisearch Node.js 移植 + grep/py/js 三方基准测试报告

> 生成时间：2026-09-17 ｜ 工具版本：aisearch 0.1.0（py 与 js 同源协议）
> 语料：确定性生成（种子 20260917），270 文件 / 10,823 行 / 1,832 符号（120 .py + 90 .ts + 60 .go）

---

## 1. 摘要

| 维度 | 结论 |
|------|------|
| 移植完整性 | py ↔ js **CLI parity 24/24**、**rpc parity 14/14**，JSON 输出逐字段一致（除耗时字段） |
| 出错率 | grep / rg / py / js 四方对真值 **全部 0 出错**（373 行文本真值 + 118 符号真值 + 24 个语义用例） |
| 效率（单次 CLI） | grep 5.2ms < rg 8.9ms < **js ≈ 95ms** < **py ≈ 160ms**；js 冷启动比 py 快 **~42%** |
| 效率（纯实现符号提取，270 文件） | **js 116ms vs py 212ms**，Node 快 **1.8 倍** |
| 效率（会话批量 rpc，20 请求） | **js 238ms vs py 378ms**，Node 快 **1.6 倍**（11.9ms/请求 vs 18.9ms/请求） |
| 工程建议 | 单次查询场景 js 版优势明显；高频调用应走 rpc 会话模式，摊薄进程启动开销 |

## 3. 测试方法

- **语料**：固定种子生成，含多行签名函数、嵌套类、Go 接收器方法、TS interface/enum，确保符号范围算法被真实覆盖。查询 token 种植（定义 + 调用混合）：
  `process_data`(242 行) / `validate_config`(43) / `ZetaMatrixSync`(74) / `quantum_flux`(6) / `replay_buffer`(6) / `edge_case_TOKEN`(2)。
- **真值独立**：文本真值由朴素逐行 `indexOf` 扫描器生成（不依赖任何被测实现）；符号真值由生成器的"上帝视角" manifest 直接写入（不经过符号提取器）。
- **出错率** = (假阳 + 假阴) / 真值数；**硬错误**（崩溃/非 JSON 输出/异常退出）单独计数。
- **效率** = 冷启动中位延迟（输出丢弃，仅测完成时间）；90 个样本/方式。

## 4. T1：文本搜索（核心对比）

### 4.1 出错率（6 token，真值共 373 行）

| 方式 | 假阳 fp | 假阴 fn | 硬错误 | 出错率 |
|------|--------|--------|--------|--------|
| grep -rnF | 0 | 0 | 0 | **0.00%** |
| rg -F（原生参考） | 0 | 0 | 0 | **0.00%** |
| py aisearch grep（rg 加速） | 0 | 0 | 0 | **0.00%** |
| py aisearch grep（纯 Python） | 0 | 0 | 0 | **0.00%** |
| js aisearch grep（rg 加速） | 0 | 0 | 0 | **0.00%** |
| js aisearch grep（纯 Node.js） | 0 | 0 | 0 | **0.00%** |

四方结果与真值完全一致——包括大小写、全词、正则、扩展名过滤与低频边界 token。

### 4.2 效率（中位延迟 ms，越低越好；括号内为 P95）

| 方式 | 中位 | P95 | 相对 grep 倍数 |
|------|------|-----|----------------|
| grep -rnF（GNU） | **5.21** | 5.62 | 1.0x |
| rg -F（原生） | **8.86** | 10.45 | 1.7x |
| js aisearch（纯 Node.js） | **94.70** | 107.61 | 18.2x |
| js aisearch（rg 加速） | **97.08** | 111.08 | 18.6x |
| py aisearch（rg 加速） | 159.36 | 227.14 | 30.6x |
| py aisearch（纯 Python） | 164.34 | 233.93 | 31.5x |

**解读**：
1. **js 冷启动比 py 快 ~42%**（95ms vs 164ms）——Node 进程启动与模块装载显著轻于 Python。
2. py/js 的"rg 加速"与"纯实现"延迟几乎相同：**单次 CLI 冷启动（~90-150ms）完全淹没了搜索引擎差异**。这不是 rg 没用，而是进程开销主导。要吃到 rg 的收益必须走会话模式（见 §6 rpc）。
3. grep/rg 是单功能二进制，无项目根发现、ignore 管理、JSON 结构化、符号上下文等开销，属不同功能层次；aisearch 返回的是结构化 JSON + 语义信息（所属符号、上下文窗口），非裸文本。

## 5. T2-T5：符号级能力（py vs js vs manifest 真值）

| 测试 | 用例数 | py 正确 | js 正确 | py==js | 出错率 |
|------|--------|---------|---------|--------|--------|
| T2 符号搜索 sym（5 查询，真值 118 符号） | 5 | 5 | 5 | 5/5 | 0% |
| T2' 纯实现全语料符号提取（270 文件） | - | 211.5ms | **116.4ms** | 完全一致 | - |
| T3 查找定义 def top-1（含跨文件重名） | 10 | 10 | 10 | 10/10 | 0% |
| T4 按符号读取 cat#sym（含多行签名/类/Go 方法） | 9 | 9 | 9 | 9/9 | 0% |
| T5 上下文获取 ctx（含所属符号判定） | 5 | 5 | 5 | 5/5 | 0% |

- T2' 说明原始符号提取吞吐：**Node 版正则引擎在此负载下快 1.8 倍**。
- T4 的用例覆盖了上一轮审计修复的"多行签名截断"与"花括号配平"算法——py/js 行为逐字节一致。

## 6. rpc 会话批量（20 请求/会话，5 轮取中位）

| 实现 | 20 请求总耗时（中位） | 折合单请求 | min / max |
|------|----------------------|-----------|-----------|
| py rpc | 378.3ms | 18.9ms | 373 / 508 |
| js rpc | **238.4ms** | **11.9ms** | 229 / 250 |

会话模式下无进程冷启动，py/js 都spawn rg 做实际搜索，**js 仍快 1.6 倍**——差异来自 JSON 序列化、行协议循环与符号提取的运行时效率。js 的 max 抖动也更小（250ms vs 508ms）。

## 7. 已知行为说明（非缺陷）

1. **结果顺序非确定**：aisearch 在 rg 加速模式下转发 rg 的并行遍历顺序；当匹配数超过 `limit` 被截断时，截断子集可能随运行不同。py/js 行为等同（同源于 rg）。需要稳定顺序时加大 limit 或做排序。
2. **kind 语义**：Python 方法与 Go 接收器方法在两版中 `kind=function`（归属类由 `parent` 字段表达）；TS/JS 类方法为 `kind=method`。这是两版统一锁定的行为。
3. **单次 CLI 场景 rg 收益被启动开销掩盖**：py-rg ≈ py-pure、js-rg ≈ js-pure 属预期。评估搜索引擎本身请看 rpc 批量与 T2' 符号提取。

## 8. 结论

1. **Node.js 移植成功且行为零分歧**：7 个 CLI 命令 + rpc 全部对齐，JSON 协议逐字段一致，py 回归测试全绿，js 版另通过 24 项 CLI parity + 14 项 rpc parity。
2. **出错率：grep / rg / py / js 四方全部 0%**——在 373 行文本真值、118 个符号真值、24 个语义用例上无任何假阳/假阴/崩溃。
3. **效率排序：grep < rg < js aisearch < py aisearch**。js 在所有运行时敏感指标上稳定快 1.6-1.8 倍；与原始工具的差距来自功能层次（结构化输出/项目管理/语义上下文），而非实现低效。
4. **给 AI Agent 的建议**：交互式高频检索用 `aisearch rpc`（js 版 11.9ms/请求）；一次性脚本检查用 CLI；对延迟极敏感的裸文本 grep 场景直接用 rg/grep，需要语义（符号/定义/上下文/树）时用 aisearch。
